This report evaluates the current uncommitted changes (including tracked diffs and untracked geo-analysis modules) in [younilab-seo](file:///C:/Users/TPP06792/Documents/younilab-seo) against the rules in [AGENTS.md](file:///C:/Users/TPP06792/Documents/younilab-seo/AGENTS.md).

## Findings

### 1. Job State Machine Machine Vulnerability in mark_external_status
- **File Path & Line Numbers**: [models.py](file:///C:/Users/TPP06792/Documents/younilab-seo/packages/geo-analysis-domain/src/younilab_geo_analysis_domain/models.py#L98-L106) in [mark_external_status](file:///C:/Users/TPP06792/Documents/younilab-seo/packages/geo-analysis-domain/src/younilab_geo_analysis_domain/models.py#L89)
- **Impact**: The method permits job transitions when the current status is `SUCCEEDED` or `FAILED`. If the runner sends out-of-order or duplicate webhook callbacks, a completed job can retroactively be reverted back to `RUNNING_EXTERNAL` or flip between success and failure. This breaks state-machine invariants, leading to inconsistent reporting and data integrity issues.
- **Concise Fix**: Reject state transitions in `mark_external_status` if the job is already in a terminal state (i.e. `SUCCEEDED`, `FAILED`, or `CANCELLED`) by checking `self.status` and raising `QueryRunJobStatusError`.

### 2. Presentation Layer Bypasses Use Case in receive_external_callback and cancel_job
- **File Path & Line Numbers**: [routes.py](file:///C:/Users/TPP06792/Documents/younilab-seo/apps/geo-analysis-api/src/younilab_geo_analysis_api/presentation/http/routes.py#L402-L419) in [receive_external_callback](file:///C:/Users/TPP06792/Documents/younilab-seo/apps/geo-analysis-api/src/younilab_geo_analysis_api/presentation/http/routes.py#L403) (and [cancel_job](file:///C:/Users/TPP06792/Documents/younilab-seo/apps/geo-analysis-api/src/younilab_geo_analysis_api/presentation/http/routes.py#L393-L399))
- **Impact**: The route controllers directly fetch domain entities from the store and mutate their state (`job.mark_external_status` and `job.cancel`) instead of executing application-layer use cases (such as [ReceiveExternalRunCallback](file:///C:/Users/TPP06792/Documents/younilab-seo/packages/geo-analysis-application/src/younilab_geo_analysis_application/use_cases.py#L56)). This violates Clean Architecture boundaries, bypasses repository logging (e.g. `record_external_callback` for audit trails), and leads to data-loss risks for transaction logs.
- **Concise Fix**: Inject and execute the appropriate use case (e.g., [ReceiveExternalRunCallback](file:///C:/Users/TPP06792/Documents/younilab-seo/packages/geo-analysis-application/src/younilab_geo_analysis_application/use_cases.py#L56)) in the API routes instead of direct domain model manipulation.

### 3. Non-Normalized dedupe_key for Query Run Jobs
- **File Path & Line Numbers**: [store.py](file:///C:/Users/TPP06792/Documents/younilab-seo/apps/geo-analysis-api/src/younilab_geo_analysis_api/presentation/http/store.py#L197-L200) inside [create_job](file:///C:/Users/TPP06792/Documents/younilab-seo/apps/geo-analysis-api/src/younilab_geo_analysis_api/presentation/http/store.py#L179)
- **Impact**: The `dedupe_key` is generated by formatting `scheduled_for` using `.isoformat()`. If clients send the same scheduled timestamp represented with different timezone offsets (e.g., UTC `Z` vs local offset `+08:00`) or sub-second variations, the deduplication keys will differ. This bypasses the database unique constraint and risks duplicate task dispatching.
- **Concise Fix**: Normalize the `scheduled_for` datetime to UTC and truncate sub-second precisions before building the deduplication key string.

### 4. Missing Custom Error Handlers for RFC 7807 Problem Details
- **File Path & Line Numbers**: [app_factory.py](file:///C:/Users/TPP06792/Documents/younilab-seo/apps/geo-analysis-api/src/younilab_geo_analysis_api/presentation/http/app_factory.py#L7-L16) in [create_app](file:///C:/Users/TPP06792/Documents/younilab-seo/apps/geo-analysis-api/src/younilab_geo_analysis_api/presentation/http/app_factory.py#L7)
- **Impact**: The API factory does not register exception handlers for validation errors (`RequestValidationError`) or custom domain errors (`QueryRunJobStatusError`). Under validation errors (e.g. empty strings caught by custom DTO validators), the server will return default FastAPI 422 JSON payloads instead of the `application/problem+json` format. This violates the `AGENTS.md` mandate to prefer RFC 7807 Problem Details.
- **Concise Fix**: Define and register custom exception handlers for validation and domain exceptions inside the API creation workflow to format failures into standardized Problem Details.
