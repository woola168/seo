# 使用兩階段 Project Discovery 產生 Query Research 草稿

Query Research 頁面需要讓使用者只輸入一個公開 Project URL，先辨識 Project，再產生可編輯的自身品牌、直接競品、Topics 與 non-branded seed keywords。這項能力是 Query Generation 的輸入準備工具，不是 Runner，也不應把尚未驗證的網址內容或模型推論直接寫入正式 Project 資料。

我們決定使用同一個 `GeminiProjectDiscoveryProvider`、`google-genai[aiohttp]` client 與 `aiohttp.ClientSession`，但把兩次 Gemini 呼叫拆成兩個由前端依序觸發的 use case。Stage 1 前先以 bounded HTTP fetch 取得同一個 `projectUrl` 的 HTML，並用 BeautifulSoup 擷取 title、meta description、Open Graph、canonical、JSON-LD 與有限的 H1/H2，組成 `pageMetadata`；Stage 1 只掛 URL Context，將 `projectUrl` 與 `pageMetadata` 一併提供給模型，輸出 Project 公開名稱、描述、類型與核心產品或服務。URL Context retrieval 成功，或 HTTP metadata 至少包含 title、Open Graph title、H1/H2 或 JSON-LD name 時，視為已取得來源；若兩者都沒有名稱線索、無法確認正式名稱或描述、沒有任何 core offering，或 `sufficientContext=false`，application service 回報內容不足。網頁內容與 metadata 都視為不可信來源，不能只依 domain、URL path、repository name 或模型既有知識補齊身分。

Stage 1 通過後，Admin Portal 顯示可編輯的 Project 名稱、業務描述與 core offerings。只有使用者確認後才呼叫 Stage 2；application service 將 confirmed payload 清理後建立 immutable `VerifiedProjectIdentity`。Stage 2 只掛 Google Search，將使用者確認的身分連同 Query Research 頁面的 region、language、market type 與目標數量傳入，不重新讀取 URL，也不得重新命名或改寫 confirmed Project。競品只接受相同市場中針對相同核心產品、服務或需求形成直接替代的對象；Topic 必須包含名稱與生成約束描述；keyword 必須是 non-branded seed phrase，不是完整問句。數量是 target，不是最低保證，市場資料不足時允許回傳較少項目。Query Generation 的 `audience` 不屬於 Project Discovery contract，也不得放入 Stage 2 prompt。

Application service 負責 deterministic cleanup，包括 trim、去重、以 `projectName` 排除自身 Project、從 keyword 排除自身與已選競品名稱，以及套用 request count 上限；缺少描述的 Topic 不得進入 draft。這個 MVP 不推論或保存其他 alias，若未來需要多名稱判斷，應由 `geo-analysis` 的 Entity / Alias model 提供。Search grounding 若有 `groundingChunks`，references 使用來源站 title 與 URL；Vertex structured output 只有 Search Entry Point 而沒有 chunks 時，adapter 只解析 Google 官方提供的搜尋 query 與 grounding redirect，標示為 `Google Search: <query>`。不得要求模型自行拼接 citation URL，因為 live 驗證曾出現文章標題配網站首頁的錯誤組合。

HTTP 邊界使用 `POST /api/v1/geo-tracking/project-discovery/inspection` 與 `POST /api/v1/geo-tracking/project-discovery/suggestions`。公開 URL contract 會拒絕 credential-bearing URL、localhost、`.local` 與明確的非公開 IP。Metadata fetch 另以 public-only DNS resolver 拒絕解析至非公開 IP，逐次驗證最多三次 redirect，只接受 80/443、HTML content type、15 秒 timeout 與解壓後最多 2 MiB response；不載入外部資源，也不執行 JavaScript。內容不足或 confirmed identity 不完整回 RFC 7807 `422`；provider、retrieval 或 market research 失敗回 `502` 與安全錯誤碼，不暴露 SDK exception。

Admin Portal 分別保存 identity draft 與 suggestions draft。Stage 1 的名稱、描述與 core offerings 可編輯；修改後會清除既有 Stage 2 結果。地區、市場語境或 target counts 改變時只清除 Stage 2；URL 或語言改變時兩階段都清除。使用者最終確認後才原子取代目前表單的自身品牌、競品、Topics 與 Keywords，並清除既有 generated queries、Shortlist 與 Runner results。搜尋依據只顯示在 Stage 2，不混入 Runner references。這個 MVP 不新增 DB schema 或 CRUD，重新整理頁面會遺失 draft；後續若需要保存或套用到正式 Project，ownership 屬於 `geo-analysis` 的 Project / Entity / Topic / Keyword 管理。

這個設計的代價是使用者需要明確確認一次，完整流程包含一次 bounded HTML fetch 與兩次模型呼叫，增加互動步驟、latency、網路處理責任與成本；好處是錯誤身分不會直接污染市場建議，Stage 2 失敗也不必重新執行 Stage 1。URL Context 無法讀取但公開 HTML 含有 title 或結構化 metadata 時，仍可完成第一階段。單次同掛 URL Context 與 Google Search 的方案不採用，因為目前 Vertex AI 不支援所需的 Interaction API 流程，也無法提供相同的人為確認與階段式驗證邊界。完整 crawler、headless browser 與 JavaScript rendering 不在本 MVP 範圍。
